# Family Touch build 47 — reliability and security audit (2026-11-07)

Base: `feature/family-touch-map-live-location-20261102` at 57df266 (build 46).
Version: versionCode 47, versionName `0.3.30-call-reliability`.

## Fixed

| Area | Problem | Fix |
| --- | --- | --- |
| 1:1 calls | Offer/answer/ICE/hangup were handled on the network (IO) thread while the UI and WebRTC used the main thread. A remote hangup could dispose the PeerConnection mid-use. | PeerService now dispatches 1:1 call signals to the main thread, as group calls already did. |
| 1:1 calls | `pendingIce`/`hasRemoteDescription` raced with the WebRTC signaling thread; a candidate arriving during `setRemoteDescription` could be lost (call stuck "connecting") or crash the list. | Guarded by a lock; the drain is atomic. |
| 1:1 calls | The 45 s "no answer" timer matched only the peer, so it could hang up a newer call to the same person. | Timer is tied to the exact call session. |
| 1:1 calls | Calling a busy or unreachable phone rang for 45 s with no outcome. | Busy phones now reply `busy`; the caller ends immediately with "X is on another call" or "X could not be reached". Older builds keep the old behaviour. |
| 1:1 calls | SDP failure callbacks called `hangup()` on the WebRTC signaling thread (WebRTC can deadlock when a PeerConnection is closed from its own callback). | Moved to the main thread. |
| Pairing | Anyone holding an invitation could re-pair using an existing contact's device ID from another tailnet device, replacing that contact's address and token (messages/calls would go to them). | Re-pairing an existing identity is only accepted from the same tailnet address. |
| Pairing | Secrets/tokens were compared with `==`. | Constant-time comparison. |
| Peer service | Unlimited concurrent inbound connections. | Capped at 32; extra connections are closed. |
| Storage | `FamilyStore` was mutated from both main and IO threads with index-based read-modify-write; a concurrent delete could overwrite the wrong message. | Mutators are synchronized. |
| Storage | Every change re-serialized up to 5000 messages to JSON on the caller's thread (UI jank on large chats, many writes during receipt bursts). | Writes are coalesced on one background thread. |

Unit tests added: `PairingHardeningTest`. Broker: `go vet` (Linux + Windows) and `go test` pass; no broker changes.

## Not verified here

- Compiled and unit-tested by GitHub CI only. The audit sandbox has no Android SDK, signing key or device access.
- Physical acceptance from the release gate still applies: two-device call ring/connect/busy/unreachable, paired messaging and receipts, before production promotion.

## Recommended next (not implemented)

- Full-screen incoming-call intent on the lock screen. This needs a dedicated call activity so the lock screen never exposes chats; it should be designed and checked on a device first.
- Move chat storage from one SharedPreferences JSON blob to a database (Room) for large histories.
- Rotatable pairing secret: invitations currently remain valid indefinitely.
